# SW 검증 보고서: 전자식 차일드락 제어 SW

| 항목 | 내용 |
|---|---|
| 문서 ID | VER-ECL-001 |
| 버전 | 1.0 (기준선 BL-VER-1.0 후보) |
| 대상 | 기준선 BL-INT-1.0의 `src/childlock` |
| 테스트 베이시스 | SWRS-ECL-001 v1.2 (BL-SWR-1.2), QA-ECL-001 |
| 시험 케이스 | `시스템테스트케이스_ECL.xlsx`, `시스템테스트명세_ECL.json` (같은 폴더) |
| 자동 시험 | `tests/system/test_stc_f001_040.py`, `test_stc_f041_080.py`, `test_stc_f081_118_nf.py`, `test_determinism.py` |
| 프로세스 | A-SPICE SWE.6, ISO 26262-6 Clause 11 (PC/SIL 범위) |
| OEM Gate | G4 |

## 1. 방법

1. **케이스 설계:** `system-test-case-generator` 서브에이전트가 `sw-system-test-case` 스킬로 SWRS v1.2에서 시스템 테스트 케이스를 만들었다.
   - 결함 발견을 목표로 했다. 우선순위 상호작용, 시간 경계, 필드 오류·순서 무효, override 수명, PENDING, HTTP 경계를 겨냥했다.
   - 사용한 기법: 경계값 분석, 동치 분할, PICT 페어와이즈(모델 4개), WoW 검증, 상태 전이, 폴트 주입, 성능 측정
2. **자동화:** 125건 전부를 pytest로 옮겼다(TC 1건 = 시험 함수 1개).
   - 작업은 별도 에이전트 3개가 나눠 했다. 에이전트는 제품 코드를 고칠 수 없게 했다.
   - 실패가 나면 SWRS와 대조해 "TC 오류"와 "제품 결함"을 나누도록 했다.
3. **판정:** SIL은 `ChildLockController` 출력, Web은 `/api/tick`·`/api/status`·`/api/events` 응답으로만 판정했다(DR-18). 시뮬레이터 화면은 판정에 쓰지 않았다.
4. **실행 환경:** Windows 11, Python 3.12.10. 같은 시험을 Jenkins 품질 게이트에서도 돌린다.

## 3. TC 정정 (오류 수정 목록)

자동화 과정에서 SWRS와 대조해 아래 기대값을 정정했다. 정정 내용은 시험 코드에 `TC 정정:` 주석으로 남겼다. 엑셀·JSON 명세 v1.0은 그대로 두고 이 표를 정오표로 쓴다.

| TC | 명세 v1.0 기대값 | 정정값 | 근거 (SWRS v1.2) |
|---|---|---|---|
| STC-F-044 Step 2 | WC 미표기(기본 NONE) | WC=SENSOR_FAULT | 3.3 warning_code: sensor_fault 유효값이 TRUE이면 state와 관계없이 |
| STC-F-047 (100.49) | WC 미표기 | WC=SENSOR_FAULT | SWR-021: DEGRADED여도 sensor_fault TRUE이면 SENSOR_FAULT |
| STC-NF-001 맥락 B | IV 미표기(기본 VALID) | IV=STALE | 3.3: STALE이 INVALID보다 우선, SWR-013 갱신 지연 |
| STC-NF-001 맥락 C | IV 미표기 | IV=INVALID | 3.3: 오류 필드·형식 오류 명령이 있으면 INVALID |
| STC-NF-002 진입 틱 | IV 미표기 | IV=STALE | SWR-013: DEGRADED 진입 틱의 input_validity=STALE |
| STC-NF-003 | 시나리오 구간을 한 인스턴스에서 이어 재생한 출력을 각 TC 기대값과 비교 | 시나리오마다 새 인스턴스로 비교 (해시는 이어 재생으로 판정) | SWR-007: EMERGENCY 래치가 다음 구간까지 남음 |

**명세 서식 오류:** STC-F-021 절차 1단계의 `%s` 자리가 비어 있다. 괄호의 "(좌/우 LOCK)"에 맞춰 `BASE+CMD(all,lock,physical_button)`으로 해석했다.

## 5. 시험 가정과 처리 결정

케이스 생성 에이전트가 올린 확인 사항(TQ)을 아래와 같이 처리했다(개발 계획서 D-06: 권장안대로 진행).

| ID | 내용 | 처리 |
|---|---|---|
| TQ-01 | PENDING만 걸린 도어의 reason | 판정 제외로 시험. 구현은 NO_CHANGE. OEM 질의 Q-25 |
| TQ-03 | 래치 1.0 s 계산 시작 기준 | 첫 연속 최신 틱부터 셈 (SWR-007, 통합 시험 IN-01과 같음) |
| TQ-05 | 정확히 0.5 µs 반올림 | float로 만들 수 없는 입력이라 시스템 시험에서 제외. SWRS 2장에 Python `round`로 명시함 |
| TQ-06 | snapshot 키 누락, 비객체 snapshot, 알 수 없는 URL | 단위 시험으로 검증됨: DD-02(누락=입력 없음), 비객체=모든 필드 오류(200 INVALID), 404 |
| TQ-07 | 응답 직렬화 실패 500 | 공개 API로는 일으킬 수 없다. 단위 시험의 오류 주입으로 검증됨(`test_serialization_failure_is_500`) |
| TQ-08 | DEGRADED 중 새 접근위험이 잠기지 않음 | 사양대로 시험. 안전 관점의 OEM 판단 요청 Q-26 |
| TQ-13, TQ-14 | 장시간 응답 시간 증가 3배 이하, 제한 시간 허용 범위 4.5~6.0 s | 시험 가정값으로 승인 |
| TQ-02, 04, 09~12, 15 | 사양에 명시되지 않은 해석 | 생성 에이전트의 해석(현재 구현 동작)을 시험 기대값으로 채택하고 엑셀 "가정 및 질의" 시트에 기록 |

## 7. 검증하지 않은 범위

| 범위 | 이유 |
|---|---|
| HIL, 실차, 타깃 ECU, 실시간성 | 프로젝트 범위 밖 (OEM-SWR-001 1.3) |
| 도어 래치·구동기 물리 동작, 실제 CAN/LIN | 범위 밖. 출력은 논리값 LOCK/RELEASE까지 |
| 법규 적합성 (자동차규칙 별표 14 등) | 차량·부품 물리 시험 대상. PC/SIL로 대체할 수 없음 |
| 시뮬레이터 화면(JS) | SW 경계 밖 요소. 판정 근거가 아님 (SWA 4.1) |
| ISO 26262 Table 13의 HIL·차량 환경 | PC/SIL만 사용 |

## 9. 결론

SWRS v1.2의 SW 요구사항 21건이 PC/SIL과 Web 환경에서 시스템 테스트 케이스 125건으로 모두 검증되었다. 제품 결함은 발견되지 않았다. 잔여 문제(8장)와 검증하지 않은 범위(7장)를 명시한 상태로 기준선 BL-VER-1.0을 확정할 수 있다. 다만 G4 수용은 OEM-A Verification Owner가 해야 한다.
