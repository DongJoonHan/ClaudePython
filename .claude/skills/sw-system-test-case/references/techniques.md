# 테스트 기법 적용 가이드

이 스킬에서 쓰는 기법명은 아래와 같고, `techniques` 필드에는 이 철자 그대로 적습니다.
`경계값 분석`, `동치 분할`, `페어와이즈(PICT)`, `WoW 검증`, `요구사항 분석`, `오류 추측`, `폴트 주입`, `상태 전이`, `기능 의존성 분석`, `운용 시나리오 분석`, `성능 측정`

한 TC가 여러 기법을 동시에 만족하면 기법을 모두 적습니다. 예를 들어 상한 경계값이 유효 클래스 대표값도 겸하면 `["동치 분할", "경계값 분석"]`처럼 적습니다. 기법 하나당 TC 하나를 따로 만들 필요는 없습니다. 같은 값을 같은 목적으로 두 번 테스트하면 쓰레기 케이스가 됩니다.

## 1. 동치 분할 (필수)

1. 요구사항에서 입력(신호, 파라미터, 명령, 모드)과 그 값 범위를 모두 뽑습니다. 출력 쪽 클래스도 봅니다. 출력이 다르게 나오는 구간이 곧 입력 클래스입니다.
2. 유효 클래스와 무효 클래스로 나눕니다. 무효 클래스에는 범위 밖, 정의되지 않은 열거값, 무효 신호(타임아웃, CRC 오류, Signal Invalid 값)가 들어갑니다.
3. 유효 클래스는 한 TC에 여러 개를 결합해도 됩니다. 무효 클래스는 TC 하나에 하나만 넣습니다. 둘을 함께 넣으면 한 오류 처리가 다른 오류를 가려서, 어느 쪽이 검증됐는지 알 수 없습니다.
4. 대표값은 클래스 경계에서 떨어진 값을 고릅니다. 경계 쪽은 경계값 분석이 담당합니다.

## 2. 경계값 분석 (필수)

- 범위 [min, max]가 있는 입력마다 **min−δ, min, max, max+δ**를 테스트합니다. δ는 신호의 분해능(LSB, 스텝)입니다. 분해능이 명세에 없으면 지어내지 말고 "가정 및 질의"에 올린 뒤, 사용한 가정값을 TC에 적습니다.
- 요구사항이 "초과/이상", "미만/이하"를 구분하면 경계 바로 양쪽 값이 가장 중요합니다. 경계에서 판정이 바뀌는지 확인하기 위해서입니다.
- **시간 경계**도 경계값입니다. "200 ms 이내 응답", "3초 이상 유지 시 진입" 같은 조건은 지속 시간을 경계 직전과 직후로 나눠 테스트합니다. 측정 허용오차도 명시합니다.
- **히스테리시스**가 있으면 상승 방향 임계와 하강 방향 임계를 각각 테스트합니다.
- 경계값이 동치 클래스의 대표값을 겸할 수 있으면 TC를 합쳐 중복을 피합니다.

## 3. 페어와이즈 — 반드시 PICT로 도출

**적용 판단:** 서로 독립적으로 변하는 입력 파라미터가 3개 이상이고 각각 값이 2개 이상이며, 조합에 따라 동작이 달라질 수 있을 때 적용합니다. 모든 조합을 다 테스트하면 너무 많아질 때가 대표적입니다. 파라미터가 2개뿐이면 전수 조합이 곧 페어와이즈이므로 PICT가 필요 없습니다. 이때는 동치 분할로 처리합니다.

**절차:**
1. PICT 모델 파일을 작성합니다. 값에는 동치 클래스 대표값과 경계값을 씁니다. 실제 값을 쓰는 이유는 생성된 조합이 그대로 실행 가능한 입력이 돼야 하기 때문입니다.
   ```
   # model_F012.txt
   전원모드: ACC, IGN_ON, CRANK
   차속_kph: 0, 3, 120
   도어: 열림, 닫힘
   기어: P, R, D

   # 물리적으로 불가능한 조합 제거 (실행 불가 케이스 방지)
   IF [전원모드] = "ACC" THEN [기어] = "P";
   IF [기어] = "P" THEN [차속_kph] = 0;
   ```
   - 모델 파일은 UTF-8(BOM 유무 무관)로 저장합니다. 한글 파라미터명과 값도 동작합니다.
   - **제약 조건(IF … THEN …)으로 현실에서 불가능한 조합을 반드시 제거합니다.** 예를 들어 P단에서 120 km/h는 만들 수 없습니다. 이런 조합은 실행할 수 없는 케이스가 됩니다.
   - 무효값은 페어와이즈에 섞지 않습니다. 넣으려면 PICT의 `~` 접두사를 써서 무효값 하나씩만 들어가게 합니다. 그 외에는 동치 분할의 무효 클래스 TC로 따로 다룹니다.
2. 실행합니다.
   `python <skill>/scripts/run_pict.py model_F012.txt --out pict_F012.json`
   PICT가 없으면 `ensure_pict.py`가 GitHub 공식 릴리스(microsoft/pict)에서 자동으로 설치합니다.
3. 생성된 각 행을 TC 하나로 만듭니다. 각 행의 예상 출력은 요구사항에서 직접 계산해 적습니다. "조합 결과 확인"처럼 쓰면 판정할 수 없습니다.
4. 명세 JSON의 `pict_models`에 `id`, `model_text`, `command`, `rows`를 그대로 넣고, 해당 TC들에 `"pict_model": "<id>"`를 답니다. 행을 직접 만들거나 수정하지 않습니다. PICT로 도출했다는 사실이 재현 가능해야 하기 때문입니다. 어떤 행이 다른 TC와 완전히 같아서 합쳤다면, 그 사실을 모델의 `notes`에 적습니다.

## 4. WoW 검증 (엣지 케이스)

경계값 분석이나 동치 분할의 기계적 규칙으로는 나오지 않는 **극단적 상황과 예외 상황**을 다룹니다. 실제 필드에서 결함이 자주 나는 곳입니다. 기법 열에는 `WoW 검증`이라고 적습니다. 요구사항이 직접 요구하지 않는 엣지 케이스라면 `proposed: true`로 "제안" 표시도 합니다.

관점 목록에서 해당 요구사항에 의미가 있는 것만 고릅니다:
- **타이밍:** 이벤트가 동시에 발생함, 판정 시간 창 경계에서 입력이 바뀜, 아주 짧은 펄스나 채터링, 같은 명령의 빠른 반복
- **상태/모드 전환:** 동작 도중 모드가 바뀜(예: 실행 중 IGN OFF), 상태 전이 중 재요청, 허용되지 않은 전이 시도
- **전원/리셋:** 동작 중 전원 차단 후 재기동, 저전압·과전압 구간 진입과 복귀, 웜 리셋 뒤 상태 복원
- **통신:** 신호가 사라졌다가 복귀함, 값이 중간에 무효로 바뀜, 메시지 순서가 뒤바뀌거나 중복 수신됨
- **자원/누적:** 장시간 연속 동작, 카운터 오버플로, 버퍼가 가득 참, 최대 부하 조건
- **복합 고장:** 고장이 감지된 상태에서 두 번째 고장이 발생함, 고장 해제와 재발생이 반복됨

각 WoW 케이스는 **왜 위험한지**(테스트 목적)와 **판정 가능한 예상 결과**를 가져야 합니다. 그런 결과를 쓸 수 없는 상황이면 만들지 말고, "가정 및 질의"에 요구사항 보완 질의로 올립니다.

## 5. 기타 기법 (해당 시)

- **상태 전이:** 요구사항이 상태 기계를 정의하면, 모든 유효 전이를 한 번 이상 테스트합니다(0-switch 커버리지). 주요 무효 전이도 테스트합니다.
- **폴트 주입:** 안전 메커니즘(감지, 반응, 안전 상태 진입)을 요구하는 항목에 적용합니다. 주입 방법(신호 단선, 값 고정, 메시지 차단 등)과 고장 반응 시간 기준을 명시합니다.
- **성능 측정:** 비기능 요구사항(응답 시간, 처리량, CPU/메모리 사용률)에 적용합니다. 측정 조건(부하, 반복 횟수)과 판정 통계(최댓값, 95 백분위수 등)를 명시합니다.
