# SW 시스템 테스트 케이스 생성

요구사항(테스트 베이시스)을 입력받아, 심사(A-SPICE)와 안전 평가(ISO 26262)에서 그대로 쓸 수 있는 테스트 케이스 엑셀을 만듭니다.
좋은 결과물은 세 가지를 만족합니다. **모든 요구사항이 빠짐없이 검증되고**, **모든 케이스가 실제로 실행해 판정할 수 있으며**, **의미 없는 케이스가 하나도 없습니다.** 이 세 가지는 서로 긴장 관계입니다. 커버리지를 채우려고 쓸모없는 케이스를 늘리거나, 판정할 수 없는 케이스로 숫자를 맞추지 않도록 아래 절차를 따르세요.

스크립트 경로의 `<skill>`은 이 SKILL.md가 있는 디렉터리입니다.

## 0. 입력 확인

- **테스트 베이시스:** SW 요구사항 명세(docx, xlsx, pdf, md, ReqIF, 붙여넣은 텍스트 등). 없으면 요청합니다. 추측해서 만들지 않습니다.
- **양식:** 사용자가 테스트 케이스 양식(엑셀 템플릿, 또는 열 목록)을 줬으면 그 양식을 따릅니다. 없으면 기본 양식을 씁니다.
  - 기본 양식의 열: 테스트 케이스 ID · 구분(기본/제안) · 테스트 베이시스 ID · 테스트 목적 · 사전 조건 · 테스트 환경 · 입력값 · 절차 · 예상 출력값 · 사용한 테스트 기법
  - 사전 조건과 테스트 환경은 실행 가능성과 ISO 26262-6 Table 13(테스트 환경) 때문에 들어 있습니다.
- **실행 환경:** Python과 `openpyxl`이 필요합니다(`python -m pip install openpyxl`). PICT는 페어와이즈가 필요할 때 `scripts/ensure_pict.py`가 GitHub 공식 릴리스에서 설치합니다.

## 1. 베이시스 분해

요구사항을 **검증 가능한 단위 항목**으로 나누고, 각 항목에 ID를 붙여 목록을 만듭니다.
- 문서에 ID가 있으면 그대로 씁니다. 없으면 `문서약어-절번호-순번` 형식으로 붙이고, 붙인 규칙을 사용자에게 알립니다.
- 한 문장에 조건이 여러 개 있으면 조건마다 따로 확인할 수 있어야 합니다. 예: "A이고 B이면 X를 C ms 이내에 수행" → 기능 조건과 시간 조건. 항목을 하위 ID로 쪼개거나, 같은 ID 아래 각 조건을 검증하는 TC를 따로 둡니다.
- 항목마다 `type`(기능/비기능)을 정합니다. 비기능에는 응답 시간, 주기, 자원 사용, 강건성, 시동·종료 시간, 진단 응답 시간 같은 것이 들어갑니다. 기능 안전 메커니즘의 동작(감지 → 반응)은 기능으로 분류하고, 반응 시간 요건은 비기능으로 분류합니다.
- 시스템 레벨에서 테스트할 수 없는 항목(코딩 규칙, 내부 구조 등)은 TC를 지어내지 않습니다. `not_testable_reason`과 대안 검증 수단을 적고, 사용자에게 보고합니다.
- 테스트에 필요한 정보가 빠져 있으면(분해능, 허용오차, 타이밍, 무효값 정의 등) 테스트를 실행할 수 없게 됩니다. 확인할 수 있으면 사용자에게 묻습니다. 일괄 작업이라면 합리적인 가정값으로 진행하되, 그 가정을 `assumptions`에 기록하고 영향받는 TC를 적습니다.

## 2. 케이스 설계

먼저 `references/techniques.md`를 읽으세요. 기법별 적용 규칙, PICT 모델 작성법, WoW 관점 목록이 있습니다.

항목마다 다음 순서로 설계합니다.
1. **동치 분할 (필수):** 유효 클래스와 무효 클래스를 모두 다룹니다. 무효 클래스는 TC 하나에 하나만 넣습니다.
2. **경계값 분석 (필수):** 값 범위, 임계값, 시간 조건의 경계 양쪽을 테스트합니다. 입력 범위가 전혀 없는 항목이면 `ep_bva_na_reason`에 사유를 적습니다.
3. **페어와이즈 (가능하면 적용):** 상호작용하는 독립 파라미터가 3개 이상이면 적용합니다. **조합은 반드시 PICT로 만듭니다.**
   `python <skill>/scripts/run_pict.py <model.txt> --out <result.json>`
   조합을 손으로 만들면 "PICT로 도출"이라는 근거가 사라지고 재현할 수도 없습니다. 제약 조건으로 물리적으로 불가능한 조합을 제거합니다.
4. **WoW 검증 (엣지 케이스):** 타이밍, 모드 전환, 전원·리셋, 통신 단절, 누적, 복합 고장 중에서 이 요구사항에 의미 있는 극단 상황을 테스트합니다. 기법명은 `WoW 검증`으로 적습니다.
5. **기타:** 상태 기계가 있으면 상태 전이를 테스트하고, 안전 메커니즘(특히 ASIL C/D)에는 폴트 주입을 적용하고, 비기능 항목에는 성능 측정을 적용합니다.

### "제안" 표시

베이시스가 직접 요구하지는 않지만 여러분의 판단으로 추가하는 케이스에는 `proposed: true`를 줍니다. 엑셀의 구분 열에 **제안**으로 표시되고 행이 노란색이 됩니다. 대부분의 WoW 케이스, 명세에 없는 무효값이나 강건성 시나리오가 여기에 해당합니다.
제안 케이스도 가장 관련 있는 베이시스 ID로 추적되게 합니다. 테스트 목적에는 그 케이스가 어떤 위험을 겨냥하는지 적습니다.
제안 케이스는 커버리지 달성에 필요하지 않습니다. 그래서 정말 결함을 찾을 가능성이 있는 것만 넣습니다.

### 실행 가능성 기준

테스트 엔지니어가 이 시트만 보고 실행해서 합격과 불합격을 판정할 수 있어야 합니다.
- **입력:** 신호명이나 파라미터명과 구체적인 값, 단위, 유지 시간을 적습니다. "높은 차속"처럼 쓰지 말고 "VehicleSpeed = 120 km/h"처럼 씁니다.
- **절차:** 순서대로 실행할 수 있는 단계로 씁니다. 사전 조건을 만드는 방법도 포함합니다.
- **예상 출력:** 관측할 수 있는 신호, 상태, 값과 허용오차, 그리고 시간 조건을 적습니다. "정상 동작한다", "올바르게 처리한다" 같은 표현은 판정할 수 없으므로 쓰지 않습니다.
- **환경:** 그 테스트가 실제로 가능한 환경(SIL, HIL, 차량 등)을 적습니다. 예를 들어 전원 차단 테스트가 SIL에서 가능한지 같은 점을 따져 봅니다.
- 이 기준을 만족하도록 쓸 수 없는 케이스는 만들지 않습니다. 대신 질의로 올립니다.

### 쓰레기 케이스를 만들지 않는 기준

TC 하나하나가 **다른 TC로는 잡을 수 없는 결함**을 겨냥해야 합니다. 다음은 넣지 않습니다.
- 같은 동치 클래스에서 대표값만 바꿔 반복하는 케이스
- 다른 TC와 사전 조건, 입력, 예상 결과가 같은 케이스
- 요구사항 문장을 "확인한다"로 바꿔 적기만 하고 구체적인 입력과 판정이 없는 케이스
- ID를 연결하려고 실제로는 그 요구사항을 검증하지 않는 케이스에 베이시스 ID를 덧붙이는 것(일관성 위반)

## 3. 명세 JSON 작성과 엑셀 생성

1. `references/spec_format.md` 형식으로 명세 JSON을 작성합니다. TC ID는 기능은 `STC-F-001`, 비기능은 `STC-NF-001` 형식을 씁니다. 사용자 양식에 ID 규칙이 있으면 그 규칙을 따릅니다.
2. 엑셀을 만듭니다.
   ```
   python <skill>/scripts/build_workbook.py spec.json <출력>.xlsx [--template 고객양식.xlsx]
   ```
   스크립트가 다음을 기계적으로 검사합니다.
   - 추적성: 존재하지 않는 ID를 참조하는지, 추적되지 않는 TC가 있는지
   - 커버리지: 미커버 베이시스 항목
   - 필수 항목 누락, ID 중복
   - 필수 기법(경계값, 동치) 적용 여부
   - 페어와이즈 TC의 PICT 근거
   - 모호한 예상 결과, 중복 의심 케이스
3. 종료 코드가 2이면 오류를 고친 뒤 다시 실행합니다. **경고도 하나씩 검토합니다.** 경고는 쓰레기 케이스나 실행 불가 케이스의 신호인 경우가 많습니다.
4. 미커버 항목이 남으면 TC를 추가해 해결합니다. 정말 시스템 테스트로 검증할 수 없는 항목이라면 사용자에게 알리고 승인을 받은 뒤에만 `--allow-gaps`를 씁니다. 이 경우 커버리지가 100%라고 보고하지 않습니다.
5. 명세 JSON과 PICT 모델 파일은 엑셀 옆에 함께 저장합니다. 나중에 재생성하거나 감사할 때 근거가 됩니다.

출력 시트는 기능 테스트, 비기능 테스트, 추적성 매트릭스, 커버리지 요약입니다. 해당할 때만 가정 및 질의, 페어와이즈 모델 시트가 추가됩니다.

## 4. 사용자 보고

짧게 보고합니다.
- 출력 파일 경로
- 베이시스 커버리지(n/n, %)와 역추적률
- TC 수: 기능/비기능, 기본/제안
- 기법별 사용 횟수, PICT 모델 수
- 시스템 테스트로 검증할 수 없는 항목과 그 사유
- 사용자 확인이 필요한 가정과 질의 목록. 이 항목들이 확정돼야 해당 TC의 값이 확정된다는 점을 함께 알립니다.

감사 근거나 표준 조항 대응을 물으면 `references/standards.md`를 참고해 답합니다.
